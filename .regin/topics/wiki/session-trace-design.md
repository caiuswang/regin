## Session trace design

regin captures every coding-agent session as an OpenTelemetry-style trace: one `trace_id`, many spans, and a denormalized per-session aggregate row that keeps the dashboard list cheap. The pipeline is capture → ingest → read-time reconcile → render, and this page is the map of it; deep mechanics live in the sibling topics linked at the bottom.

## Data model (`lib/orm/models/trace.py`)

- **`session_spans`** — the single source of truth. One row per operation (`prompt`, `tool.Edit`, `rule.check`, `subagent.start`, `session.start`, …) with `trace_id`/`span_id`/`parent_id`, timing, a JSON `attributes` blob, status, and per-tool token attribution (plus the `tool_use_id` / `turn_uuid` linking a span back to the turn that billed it).
- **`session_trace_map`** — a skeleton mirror of those rows without the heavy `attributes`. The frontend loads the whole tree shape from here and hydrates attributes lazily, per span.
- **`sessions`** — one row per `trace_id`, incrementally maintained at ingest. Title, status, timestamps, rollup counters, token/context aggregates, and `active_work_ms` (the union of root-span intervals). `origin` is a multi-value axis (`session`, `workflow`, `llm-stage`, `topic-proposal`) from which the list view derives a builtin **category**; `agent_type` records the vendor only.

Side tables hang off the trace: `turn_usage` (one row per assistant turn, keyed `(trace_id, turn_uuid)` — turns have no causal parent and no duration, so they are not spans), `skill_reads`, `plan_sessions`, `prompt_images`, `session_tags` (custom tags; the builtin category is derived from `origin`, not stored), and `session_repos` — the multi-repo join, populated only from high-signal spans (the `session.start` cwd, any `cwd.changed`, a file-mutating tool) so an incidental read into another repo never tags the session.

## Capture path

Hook handlers translate agent hook events into span batches. `session_lifecycle.py` is the one this page owns: it emits the `session.start` / `session.end` markers — recording the starting `cwd`, the model (with its `[1m]` variant suffix) and the provider `agent_type` — reconstructs the harness's injected git-status block as an `environment.git_status` span, and, for providers whose adapter sets `synthesizes_session_end_from_stop`, synthesizes a `session.end` from `Stop` when no real SessionEnd ever fires. The rest of the handlers cover prompts, pending/resolved tool spans and payload normalization, and the `turn_trace/` package scans the transcript JSONL to synthesize the turn, assistant-response, server-tool and system spans no hook reports. Builder registry, payload schemas and provider quirks are [[trace-span-capture]]; token and cost accounting is [[trace-usage-billing]].

Every route terminates at the ingest API: handlers POST batches to `/api/spans` (`web/blueprints/trace/spans_ingest.py`), which delegates to `ingest_session_spans` in `lib/trace/trace_service/ingest.py`. That module owns the `ON CONFLICT DO UPDATE` span upsert, the parallel `sessions` upsert that advances aggregates by counter bucket (`_span_counter_buckets` decides which counters a span name touches), and the secondary writes for status, token attribution and turn usage. It also stamps the `origin` axis and self-applies auto tags for regin's own spawned runs — all first-sighting-guarded, so a tag the user removed is not resurrected on re-ingest. `materialize_session` rebuilds the skeleton and the aggregates from scratch for one `trace_id`.

`lib/trace/repair.py` is a second recovery path for a different failure. `turn_trace` caches transcript uuids it has already attempted, so a transient ingest failure can lock those turns out permanently — every later hook fire skips them. Repair walks the transcript, finds cached uuids whose expected span set is incomplete, drops them from the cache and replays the same emission path the live hook would have taken; it is idempotent because span ingest is keyed on `(trace_id, span_id)`. The triage that leads here is [[debug-missing-trace-span]].

## Serve-time merge

`session_spans` is append-only — rows are never destructively rewritten to fix structure. Two writers disagree about the same turn: live hook events (tool timing, permissions, PreToolUse pending placeholders) and the transcript scan (the real `prompt-<uuid>` anchor, assistant responses, local commands). A placeholder and its resolved counterpart coexist on disk by design, and `merge_spans` reconciles them at **read** time as a pure function over one window — no DB writes — so projection rules ship as code and self-heal on the next read. Mechanics are [[trace-merge-reconcile]]; what the read path must know:

- A span that "disappears" or moves in the UI was superseded or misparented, never lost.
- Anything aggregating raw `session_spans` must exclude PENDING placeholder rows.
- `materialize_session` runs the bare reparent pass rather than `merge_spans` and never persists `turn_uuid`, so a NULL `turn_uuid` stays a reliable marker of an un-attributed resolved span across rematerializes.

## Read API (`web/blueprints/trace/`)

`sessions.py` serves the keyset-paginated `/api/sessions` list, session detail, the `/map` skeleton, span `children`/`content`/`ancestors`/`rewind` lookups, per-session tags, and the `materialize`, `close`, `repair-spans` and delete actions. Detail and map are backed by `fetch_session_projection` / `fetch_session_paginated` in `lib/trace/trace_service/queries.py`, raw SQL because SQLite `json_extract` and `ROW_NUMBER()` window CTEs don't translate cleanly to SQLModel. Both run their window through the serve-time merge before projecting, and the paginated reader also returns `retired_span_ids` (raw − merged) so the frontend's append-only conversation cards can prune exactly the rows the merge dropped. It pages by **turn anchors** (`prompt` spans, joined by `compact.*` and lifecycle markers) rather than by row, because the projection is only correct over a whole chronological window.

Two families of derivation happen at read time and are stored nowhere: `_row_to_dict` computes each list row's `context_pct`, `active_pct` / `idle_ms`, canonical `agent_kind` and builtin `category`, with the list query folding the origin/tag/kind/status/repo/search/date filters and their facet counts; `_session_summary` decorates detail and map with the context-window percentage, the primary repo, the phase verdict and the whole-session agent roster that both the /live card and the desktop view's agent scope consume. Sibling blueprint modules are narrower projections of the same trace (per-turn usage and tool rollup, MCP calls, skill reads, prompt images, ingest errors).

## Dashboard: the session list (`frontend/src/views/SessionsView.vue`)

A thin orchestrator; the state lives in composables. `useSessionListQuery` owns every narrowing axis, its `localStorage` key and the request it builds, driving keyset pagination against `/sessions` and omitting any value equal to the server default; date boundaries are computed in the browser's local clock and serialized as naive local ISO so the server's lexicographic string compare matches the stored text format. Facet counts come from the current window's envelope, never from global per-tag totals — a tag with no sessions in view would otherwise advertise its all-time count and outrank facets that genuinely match. Grouping is presentation-only over the rows *already loaded*, which is why a group's count and the server total diverge once the list is truncated.

The trap in the row actions is that deleting or closing a session is a trace-store write that says nothing to the process behind it: a still-running agent keeps emitting spans and reappears as a new partial trace. `useLiveShutdown` first probes which tier still holds the row (a regin-launched run, or a live agent in a tmux pane), names it in the confirmation and stops it before the row is settled. **Close** is the settle-only action for an interrupted session that never emitted a SessionEnd: status flips to ended, trace data is kept.

Rows render as a grid on desktop and cards on narrow screens. The headline **ctx %** is derived server-side from the live main-flow peak so sub-calls don't inflate the main conversation's apparent context, with an all-inclusive `+sub` badge only when the two diverge. Active-vs-idle detection is shared through `utils/sessionActivity.js` so this view, its rows and the `/live` poll cadence cannot drift apart.

## Dashboard: the per-trace view (`frontend/src/views/SessionTraceView.vue`)

The browser route is `/trace/sessions/<trace_id>`, the data API `/api/sessions/<id>/map` ([[trace_view_correct_url_and_endpoints]]). The view is an orchestrator over composables, each owning one slice; the durable parts:

- **`useTraceData`** is the core: `treeNodes`, pagination and every fetch/merge primitive, mutating the SFC-owned `session` / `selectedSpan` refs threaded in. It loads the skeleton first so the tree shape renders before heavy attributes are fetched; `useSpanContentCache` overlays on-demand `/content` fetches onto `session.spans` as one merged `allSpans` list every consumer reads.
- **Four view modes** (conversation, timeline, terminal, messages) resolved `?view=` query > `localStorage` > default.
- **Two render paths** ([[trace_dual_render_paths]]) — the invariant worth remembering. The timeline spine reads the DB-reconciled `treeNodes` keyed by id; the conversation feed (`components/SessionConversationView.vue`) is **append-only**, walking the span list by `span_id`, so a superseded placeholder lingers unless something prunes it. `useTraceData`'s live-tail reconcile is that one place — it applies `dropRetiredSpans` (`utils/traceFormatters.js`) with the `/map` response's `retired_span_ids`.
- **Reading density.** The feed's rows carry two orthogonal hiding mechanisms. *Folding* (`useConversationFolding`) collapses turns, agents and workflow subtrees structurally. *Focus mode* (`useFocusMode` + `tierOf` in `conversation/dispatch.js`) tiers each span by prominence — full card, condensed row, or folded behind a per-turn strip — and publishes a live folded count so the toggle states what it is doing. The consequence for any reveal path (a `?span=` deep link, a TOC or timeline click): revealing a row must clear **both** — unfold its owning turn/agent *and* lift its tier — or the target lands on nothing. Tier is stamped onto each row once per turn rather than recomputed per template read, because `tierOf` would otherwise run hundreds of times per live-poll re-render.
- **Presentation mode** (`usePresentReader`, `components/present/`) is a second, deliberately **unscoped** walk: it builds its own span tree over `allSpans` so ↑↓ steps through folded agents, Focus-hidden spans and other agent scopes — the point being that the reader is not limited to what the feed happens to render. A span the walk cannot resolve (a synthesized scoped prompt, or one the merge retired mid-read) is kept as a detached snapshot so the reader still opens instead of stranding an id nothing resolves. The live poll force-refetches only the one span being read, and only while it is attached, so a still-streaming body keeps growing under the write-once content cache.
- **Agent scope.** `useTraceScope` binds one roster entry to a shareable `?agent=` param that only the conversation tab applies. `TraceConversationRegion` owns the two presentations of that single state: at ≥xl the main feed stays unscoped and the scoped subtree renders in the companion `TraceAgentPane`; below xl, or when the user maximizes it, the scoped projection takes over the feed. Because the split mounts the feed twice over one `selectedSpan`, the pane must hand its embedded feed its own `scrollerGetter` and every selection is tagged with the feed that raised it — otherwise a click in the pane scrolls the main thread. The header keeps showing MAIN-session truth throughout.
- **Live sync** — a visibility-gated poll (`LIVE_POLL_MS = 4000`) fires `reloadLiveTail()` so a user parked at the bottom keeps seeing new spans and any placeholder→anchor duplicate is reconciled away. The poll is **self-terminating**: an already-closed session gets one bounded catch-up instead of the recurring poll, and a live session that ends mid-view stops once `ended_at` is set *and* the tail stops advancing. Retiring flips `liveSyncActive` false so the scroll pull-to-refresh stops re-triggering a backend transcript rescan; the ingest clearing `ended_at` on a genuine resume re-arms both.
- **Steering.** A session that is live *and* bridge-reachable renders a follow-up composer (in the feed, and as Reply from the reader). The text is POSTed to the bridge and never echoed client-side — it reaches the feed only when the poll returns its real span. Prompts typed while the agent is busy fire no hook and so cannot be spans either; they are derived server-side and shown as a transient queued banner that clears when the agent dequeues them.
- **Failure surfaces.** Every `/map`-backed loader fired from an event handler is invoked unawaited, so a rejection would be an unhandled rejection and nothing else — spans that quietly stop moving. They all run through `guarded()`, which degrades the header into a stale-data marker that only an explicit reload may clear. A failed *initial* load instead replaces the pane with a focusable retry alert rather than leaving "Loading session…" on screen forever.
- **Header.** The sticky trace header measures itself and republishes its height as a CSS var every dependent offset reads. Two guards are load-bearing: the collapse threshold is the *measured* expanded height, not a constant, and only scrolls backed by recent user input may trigger a fold — otherwise the browser's scroll-anchoring correction after the shrink feeds the state machine and collapse⇄expand oscillate forever.

Verifying a change here means rendering the real trace in a browser ([[feedback_verify_webui_in_browser]]).

## Why the shape is what it is

1. **`session_spans` is the source of truth; `sessions` is a cache.** Aggregates exist so the list view is O(1) per row; `materialize_session` exists so that cache can always be rebuilt. Never edit aggregates by hand.
2. **`session_trace_map` is the skeleton.** Splitting the JSON-heavy `attributes` off the tree shape is what makes long sessions navigable.
3. **Turns aren't spans.** Turn usage has no causal parent and no duration, so it lives in `turn_usage` keyed by `(trace_id, turn_uuid)`.
4. **Repo membership uses high-signal events only**, so an incidental cross-repo read never mistags a session ([[feedback_orthogonal_data_model_axes]]).
5. **Reconcile at read time, not write time.** The store is append-only and reconciled per read window, so projection-rule changes ship as code and never require a data migration. The price is that every raw reader must go through the merge — which is why the paginated endpoint threads `retired_span_ids` back to the append-only conversation cards.
